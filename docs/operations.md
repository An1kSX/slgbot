# Резервное копирование и перенос

Команды для Bash выполняются из корня проекта. Храните копии вне сервера;
папка `backups/` ниже — только место для подготовки копии.

## Создание копии

Нужны три части: SQL-дамп, каталог `data/` и актуальный `.env`.
На время копирования остановите бот, чтобы его файлы и БД не менялись.
Команды ниже перезаписывают одноимённые файлы копий — сохраните предыдущую копию
под другой датой перед повторным запуском.

```bash
mkdir -p backups
chmod 700 backups
docker compose stop bot
docker compose exec -T mysql sh -c 'exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction --no-tablespaces --databases "$MYSQL_DATABASE"' > backups/database.sql
sudo tar -czf backups/data.tar.gz data
cp .env backups/installation.env
docker compose start bot
```

Проверьте успешность каждой команды, ненулевой размер SQL-дампа и содержимое
архива через `sudo tar -tzf backups/data.tar.gz`. Ошибка копирования — повод
повторить копию; после диагностики верните бот в работу командой `docker compose start bot`.

## Восстановление на новом сервере

Восстанавливайте на отдельной новой установке с пустым томом MySQL и без
работающего бота. Не запускайте старый и новый сервер одновременно с одним токеном
и сессией. Скопируйте исходники и резервные копии, затем:

```bash
cp backups/installation.env .env
chmod 600 .env
sudo tar -xzf backups/data.tar.gz
docker compose up -d mysql
docker compose ps
```

Дождитесь `healthy` у MySQL, затем загрузите дамп и запустите бот:

```bash
docker compose exec -T mysql sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD"' < backups/database.sql
docker compose up -d --build bot
docker compose logs --tail=100 bot
```

Проверьте владельца восстановленных каталогов данных: UID/GID `10001`.
Проверьте `/start`, тестовое сообщение и выгрузку. Не уничтожайте исходные копии
до успешной проверки.

## Переход со старой структуры проекта

Эти шаги нужны только для уже работающей прежней версии с данными в корне.
Новая установка использует порядок из README.

1. Остановите прежний бот и сделайте резервную копию БД, конфигурации и файлов.
2. Сохраните прежнее имя проекта Compose. Если `COMPOSE_PROJECT_NAME` не было,
   посмотрите имя работающего проекта через `docker compose ls` до замены файлов
   и задайте его в `.env`. Иначе новая установка может использовать другой том БД.
3. Перенесите целиком `groups/`, `archive/`, `runtime/` в новую папку `data/`.
   Не объединяйте их вслепую с уже существующими данными новой установки.
4. Если сессия `*.session` и `logs.log` лежали отдельно в корне, поместите их
   в `data/runtime/`; имя используемой сессии должно быть `slgbot.session`.
5. Обеспечьте владельца UID/GID `10001` для перенесённых данных, проверьте `.env`
   по новому шаблону и выполните `docker compose up -d --build`.

Самые старые папки логов, названные только по имени группы, нельзя однозначно
привязать к Telegram ID. Храните их отдельно как историческую копию. Новая версия
не удаляет и не включает такие папки в дневную выгрузку. Настройка
`LOG_DATE_OFFSET_MINUTES` больше не используется.
